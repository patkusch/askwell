# Problem statement

Most requests arrive as a solution. Work back to the problem before anyone builds anything.

## Steps

1. **Translate the request.** "We need a dashboard" becomes "What decision can't you make today, and what would you look at to make it?"
2. **Ask the five things:**
   - *Who* has the problem?
   - *What* goes wrong, concretely? Get an example with a date.
   - *How often* and *how much* does it cost (hours, money, errors, lost customers)?
   - *Why now*?
   - *What happens if we do nothing?*
3. **Write it in one paragraph** using this shape:

> **[Who]** struggle to **[do what]** because **[cause]**. This results in **[measured impact]**. We will know it is fixed when **[measurable outcome]**.

4. **Check it.** It must contain no solution word (system, tool, app, portal, dashboard, AI). It must have at least one number. The person with the problem must recognise it.

## Example

Weak: "We need a new CRM."
Strong: "Account managers spend about 6 hours a week re-typing customer details between two systems, which causes roughly 40 wrong invoices a month. We will know it is fixed when wrong invoices fall below 5 a month and re-keying is gone."

## Watch for

- No number available: say so, and make "measure the baseline" the first task.
- Several problems in one: split them, and prioritise.
